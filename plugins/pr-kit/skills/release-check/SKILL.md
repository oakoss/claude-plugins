# Release check

Report what merging the release pull request would publish, so the user merges it knowing what it says. Merging it is the release, and stays the user's ask: this skill reads and reports. It never merges, edits the pull request, pushes, or changes a bump file.

## 1. Find the release pull request

The one the user named, else the open pull request whose head branch is `version-packages`, ends in `/version-packages`, or starts with `changeset-release/`:

```bash
gh pr list --state open --limit 200 --json number,headRefName,title,url
gh pr view <number> --json number,title,url,headRefName,baseRefName,mergeStateStatus,isDraft
```

With none, say so and stop: there is nothing pending, or the release workflow has not run since the last bump file landed. With several, name them and ask which.

## 2. Read what it releases

Fetch its head and base without checking either out, then read both by ref, never from the working tree, which holds the user's own branch and bump files:

```bash
git fetch origin <baseRefName> <headRefName>
git diff --name-status origin/<baseRefName>...origin/<headRefName>
git diff origin/<baseRefName>...origin/<headRefName> -- '*CHANGELOG.md'
git merge-base origin/<baseRefName> origin/<headRefName>
git diff --name-status <merge-base> origin/<baseRefName> -- .changeset
git show origin/<headRefName>:<path>
git show origin/<baseRefName>:<path>
```

- **Versions:** each package the pull request bumps, its old and new version. Read the version from every file that carries it at the head with `git show`, not from the diff: a manifest the release forgot to bump is absent from the diff. With oakum, those files are each package's manifest plus its `extra-files` in `.changeset/_config.toml`; otherwise the package's manifest and any plugin or marketplace file naming it. A file still holding the old version, or another one, is a finding naming the file and the version it holds.
- **Changelog sections:** each package's notes are the section under its new version's heading in its `CHANGELOG.md` at the head, up to the next second-level (`##`) heading. A closing line naming the tool (`Generated by …`) is never a note, nor is any other line the diff adds outside that section.
- **Consumed bump files:** the `.changeset/*.md` files the diff deletes. Read each one at the base with `git show`: one whose frontmatter names a level other than `none` is a note going out, and its filename is where a finding about it is fixed; a `none` file ships nothing. A package with a new version and no section, or a section with nothing under its heading, is a finding.
- **Out of date:** any `.changeset/*.md` besides `README.md` that the base has added, changed or deleted since the merge base was changed after the pull request was built, so the pull request does not release it as it now reads. The release workflow rebuilds it on the next push to the base branch.

## 3. Read the notes as one release

Each note was written alone; the release joins them. Read each package's section through and flag:

- **Repeats:** two notes about the same change, or one note restating another's subject.
- **Leaning on a neighbour:** a note that opens with or depends on "also", "this", "these", "the above", "as before" or "the previous change", whose referent is another note that is now elsewhere or gone.
- **Contradictions:** a later note that undoes or changes what an earlier one in the same release says, such as a feature added and then cut, where the first note now describes something that does not ship.
- **Stale claims:** a version number, count or file a note names that the release itself changes, such as "the skill runs to about 61,000 characters" when this release shrinks it.

Quote each flagged note's first words and say which note it collides with. A finding is fixed by editing the bump file on the base branch, in its own pull request; the release workflow then rebuilds this one. Never edit the release pull request's branch, which the next rebuild overwrites.

## 4. Read its state

```bash
gh pr checks <number> --json name,bucket
gh pr checks <number> --required --json name,bucket
```

Read each check's `bucket`, not the exit code. Report checks that are `fail` or `cancel` by name, and `pending` ones as still running. When none is required, the second command exits 1 with `no required checks reported`; say no check is required. When the pull request has no checks at all, the first exits 1 with `no checks reported`; say so. Report `mergeStateStatus` and `isDraft` from step 1 as they are.

When the repository lints commit messages and squash-merges with the pull request title, the title becomes the release commit's subject: run the linter on it and report the result.

## 5. Report

- **Releases:** one row per package: name, old → new version, bump level.
- **Notes:** each package's new changelog section, rendered.
- **Findings:** each one from steps 2 and 3, with the file and the fix.
- **State:** CI, merge state, draft, title.
- **Verdict:** ready to merge, or what to fix first. Merging is the user's ask: name it, and stop.
