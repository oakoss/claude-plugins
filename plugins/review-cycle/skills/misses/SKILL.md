# Consent misses

The commit gate reads each message the user types for consent to push, open a pull request, merge, release or comment on GitHub. When it refuses one of those steps and the user's latest message named that step by its verb, or replied to an offer of it, the refusal may be a miss: the user asked, in words outside the closed set of requests the gate reads. The gate keeps this session's, up to 20, and the plugin's store the newest 200 from every session and repository; nothing leaves the machine.

## Steps

1. Call the `mcp__review-cycle__misses` tool. It returns `misses`, this session's, and `recorded`, the newest 20 kept from every session, both least recent first, each with `message` (what the user typed), `offer` (the last lines of the answer their message replied to, or empty), `steps` (the steps named), `refusal` (what the gate said) and `kind`; a recorded one also has its `date` and `repo`. `counts` totals every one kept, and `recordedError`, when present, says why `recorded` is null or why `unsaved` session misses are not in it yet. An entry of `kind` `model` was kept by an earlier version and is no refusal: the gate's reader of that version granted nothing, and a model check read the message for it, quoting the words it read. It is a miss all the same. If the tool does not exist, the gate is switched off in `/config` or did not load: say so and stop.
2. Work from `misses`. When it is empty, say there are none this session and work from `recorded` instead, naming each one's date and repository; when both are empty, say so and stop.
3. For each miss, show the message, the offer when there is one, the steps and the first sentence of the refusal, or the model check's quote for one of `kind` `model`. Then draft the corpus row it suggests: `{ "prompt": "<message>", "offer": "<offer>", "may": [<STEPS>] }`, without `offer` when there is none. The offer is the lines the gate read, so the row reproduces the refusal as the gate saw it.
4. Leave `<STEPS>` for the user to decide. A miss is a candidate, not a verdict: a refusal of a message that only mentioned a step ("did the push fail?") is the gate working, and so is one of a request outside the set, which costs the user one yes to the gate's question. A phrasing the user keeps typing is a case for adding it to the set, which is their decision. Ask which rows they meant as requests, and which steps each may grant, before adding any.
5. In the review-cycle repository, add the rows the user labeled to the end of `plugins/review-cycle/hooks/consent.corpus.json` with the Edit tool, each as `{ "prompt": "<message>", "offer": "<offer>", "may": ["<step>"] }`, leaving `offer` out when there is none and `may` empty for a message that asks for nothing, and skipping a row the file already holds. Then run `pnpm exec vitest run plugins/review-cycle/hooks/consent.corpus.spec.ts`. The spec checks one thing, that the gate grants no step a row's `may` leaves out. A row that fails grants a step its label does not allow, which is a fix to make first: take the row out and tell the user. Elsewhere, show the rows for the user to add there.
